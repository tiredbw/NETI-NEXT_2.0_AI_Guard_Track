# Жизненный цикл локального детектора

Этап 7. Работающий backend остаётся локальным Ollama с qwen3.5:4b; платные и облачные API не используются.

## Startup и readiness

При запуске gateway выполняет:

1. Проверку незавершённой операции в SQLite. При наличии запись не удаляется автоматически; модель не вызывается.
2. GET /api/version, GET /api/tags и POST /api/show на фиксированный loopback Ollama.
3. Проверку наличия выбранной модели, формата digest и capability completion.
4. Один безвредный запрос со штатной JSON Schema и строгую валидацию ответа. think:false используется при заявленной capability thinking.

Startup smoke проверяет совместимость транспорта/JSON, не точность классификации. Его результат не отправляется целевому агенту. Если Ollama недоступен, gateway может работать в degraded: liveness доступна, новые проверки получают REVIEW; hard deny остаётся BLOCK.

`GET /health/ready` возвращает 200 только при готовом detector, БД, политике и retention. Модель описана полями model, digest, expected_digest, server_version, runner, quantization, active, last_error. Повторный health GET не запускает генерацию и не обращается к Ollama. Readiness проверена до первого пользовательского запроса.

Digest проверяется перед генерацией и после её завершения. Первый полученный digest закрепляется на время процесса. Для закрепления между перезапусками задайте `ASTRAGUARD_MODEL_DIGEST` — 64 lowercase hex символа из проверенной конфигурации. Несовпадение →REVIEW/DETECTOR_MODEL_CHANGED без принятия нового результата.

Это проверка метаданных доверенного локального Ollama, а не независимая аттестация весов или бинарного файла runner. Результаты аудита теперь содержат фактический закреплённый digest; при отсутствии проверенной идентичности он null.

## Таймаут и незавершённая генерация

Фоновый metadata monitor опрашивает локальный backend раз в 15 секунд без генераций. Health использует кеш с TTL 30 секунд и показывает checked_at/verification_age_seconds; просроченная успешная проверка становится stale/503. Обычный health GET сети не вызывает. После временного отказа metadata могут восстановить readiness только если structured compatibility уже была проверена. Monitor никогда не снимает quarantine/draining.

Один активный inference, максимум четыре ожидающих запроса, queue timeout 2 с. Шестой запрос или истёкшая очередь →429. Бюджет ожидающего вызова после очереди — 20 с, включая metadata; запись аудита и HTTP gateway добавляют свою задержку.

Важное отличие от простого wait_for HTTP:

- по публичному deadline запрос получает REVIEW/DETECTOR_TIMEOUT;
- исходная upstream задача остаётся под supervision с удержанием локального слота и SQLite latch;
- новые генерации в состоянии draining не отправляются;
- полученный позже результат отбрасывается для исходного запроса: исходный REVIEW не превращается в ALLOW и не исполняется;
- только подтверждённый done=true освобождает latch; после валидации detector может снова стать ready;
- drain ограничен 90 с; отсутствие подтверждения, обрыв или незавершённый response оставляют постоянный карантин;
- отмена Python caller не снимает блокировку фонового запроса;
- shutdown ждёт до 2 с, затем прекращает ожидание с сохранённым latch, если завершение не подтверждено.

ConnectError/ConnectTimeout до установленного соединения допускают безопасную повторную попытку: запрос не дошёл до сервера. Невалидный структурированный content при достоверном done=true даёт REVIEW/invalid_output, но слот можно освободить. Неопределённый transport failure, отсутствие done, незавершённый JSON или ошибка bookkeeping не разрешают новый inference.

Локальный asyncio lock сериализует вызовы. Атомарный detector_operations в SQLite предотвращает второй управляемый вызов даже из другого экземпляра с той же БД. Запись содержит только model, operation UUID, owner PID, digest и время — без prompt.

MVP запускается с одним uvicorn worker (launcher задаёт это явно). Другие программы и gateway с другой БД, напрямую вызывающие Ollama, этим latch не контролируются. Список резидентных моделей /api/ps не используется как доказательство завершения конкретного запроса.

## Карантин после сбоя

Состояние сохраняется в schema v4 и не очищается retention. Обычный рестарт gateway не запускает новую генерацию поверх неподтверждённой старой. В карантине health возвращает 503, запросы — REVIEW/DETECTOR_QUARANTINED, подтверждение кнопкой reviewer невозможно.

Локальное восстановление:

1. Остановить gateway.
2. Остановить Ollama/runner штатным способом и убедиться, что прежняя генерация больше не выполняется.
3. Выполнить команду из корня проекта:

```bash
.venv/bin/python scripts/reset_detector.py --acknowledge-backend-stopped
```

Для отдельного state directory укажите `--database /path/to/audit.sqlite3`.

4. Запустить Ollama, затем gateway.

Команда требует явного подтверждения оператора и отказывается работать, пока PID владельца жив. Она атомарно записывает событие восстановления и удаляет latch. Ошибка аудита откатывает сброс. Никакого удалённого reset endpoint нет.

Остановка backend — **подтверждение локального оператора**, не машинное доказательство: CLI проверяет PID gateway, но не аттестует завершение всех процессов Ollama. Не используйте эту команду вместо фактической остановки backend. Автоматического kill сторонних процессов нет.

## Фактические проверки

- 138 offline pytest tests passed, одно известное предупреждение TestClient backend.
- Fault-тесты с управляемым HTTP transport: публичный timeout, поздний done, отсутствие completion ack, обрыв, лимит drain, queue overflow, отмена caller, shutdown, смена digest до/во время генерации, отказ bookkeeping, сохранение карантина после рестарта и атомарное локальное восстановление.
- На API подтверждено: timeout →REVIEW, поздний benign ответ не вызывает target agent; health становится ready только после завершения supervised задачи.
- Реальный Ollama 0.40.16/MLX/nvfp4 прошёл startup; до пользовательского запроса health вернул 200 с digest 7f3251fa6878a78a606bcb3c074283306e5ad2ea411a7774a9dd98a4bc7f2d13.
- Браузерный smoke с настоящим Qwen прошёл: чтение, BLOCK без forwarding, отдельный reviewer, подтверждённая запись, admin policy update/ETag и live ACL.

Рабочий Ollama не останавливался и искусственно не подвешивался для fault-тестов. Проверены механизмы gateway; реальная скорость отмены/освобождения GPU конкретным runner не заявляется. Укороченные таймеры использовались в unit tests, а не ожидание реальных 20/90 с.

Новые Precision/Recall/latency benchmark в этом этапе не измерялись. Предыдущие оценки привязаны к версиям в EVALUATION.md. Evaluator отдельно фиксирует startup self-test и digest каждого наблюдаемого ответа.

## Основания протокола

- [Ollama Chat API](https://docs.ollama.com/api/chat): структурированный chat response, done и параметры генерации.
- [List running models](https://docs.ollama.com/api/ps): список моделей; gateway не трактует его как completion ack.

Сигнал освобождения слота выбран консервативно: явное завершение операции, а не только прекращение ожидания HTTP клиентом.
