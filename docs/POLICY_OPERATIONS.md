# Версии политик и хранение аудита

Этап 6. Политика управляется через административный API. Полный визуальный редактор политик остаётся P1.

## Доступ

Launcher создаёт локальную учётную запись `policy-admin` с ролью `policy_admin`, tenant `control`. При обновлении существующего `data/demo-access.json` добавляется только новый случайный credential; старые ключи и HMAC key сохраняются. Файл записывается атомарно с правами 0600. Ключи не печатаются и не выдаются через API.

Роль управляет **общим** профилем strict-demo-v1 для всех tenants. Credential администратора должен оставаться у оператора демонстрации. Он не получает права чтения документов, записи черновиков, подтверждения действий или чтения чужого пользовательского аудита. Назначение ролей остаётся в серверной конфигурации identities, не в YAML и не в policy API.

В UI администратор видит инструкции API и свой административный журнал. Полный editor не имитируется.

## GET и PUT

GET `/v1/policies/strict-demo-v1` с bearer credential admin возвращает JSON и сильный ETag. Viewer/reviewer получают 403 для полного содержимого; безопасный список ID/version через `/v1/policies` доступен всем authenticated identities.

Для обновления:

1. Получить текущие JSON и ETag.
2. Отредактировать разрешённые поля roles, оставив в теле **текущий** version.
3. PUT на тот же маршрут с If-Match, равным точному ETag из GET.
4. Сервер назначает следующую версию и возвращает новый JSON/ETag. Даже повторное применение одинаковых настроек создаёт новую версию.

Коды: нет If-Match →428; устаревший ETag, wildcard или несовпадающий base version →412; невалидная схема →422; неизвестный ID →404; ошибка записи аудита →503 с rollback.

Например, для временного запрета чтения viewer можно заменить его allowed_tools на пустой список. Остальные обязательные поля роли сохранить. Используйте версию/ETag из реального GET, не придумывайте их.

## Неотменяемые ограничения

- Только роли viewer/operator в редактируемой policy schema. Нельзя добавить policy_admin или reviewer.
- Только инструменты documents.read/drafts.update.
- Scope только own_tenant; граница tenant проверяется по ресурсу в серверной БД.
- Viewer не получает запись. Operator может быть ограничен до чтения/полного запрета.
- Любая drafts.update всегда требует approval, в том числе непосредственно в authorize_tool; YAML не отключает этот барьер.
- Нет произвольных regex, Python, путей ресурсов или исполняемого кода.

YAML — seed при отсутствии сохранённой политики. Parser: ≤64 КиБ, глубина ≤8, без aliases/anchors/tags/merge и duplicate keys. Затем строгая Pydantic-схема и проверки согласованности. При наличии версии в БД seed не применяется заново и не перезаписывает изменения администратора.

## Транзакции и гонки

Версии immutable в policies; active_policies хранит активную ссылку, policy_metadata — автора, время и hash новых версий. Новая версия, active pointer и audit event записываются в одной BEGIN IMMEDIATE транзакции. Из двух конкурентных обновлений одной версии побеждает одно; второе получает 412. Ошибка аудита откатывает всё.

Сервисы читают snapshots из SQLite, без изменяемого общего policy object:

- изменение во время LLM analysis →REVIEW/POLICY_CHANGED, без forwarding;
- изменение после check →повторная проверка в executor transaction; старый ALLOW не разрешает действие;
- pending/approval привязаны к hash политики; изменение перед выдачей или исполнением отменяет допуск;
- восстановление прежних прав новой версией не оживляет старое approval;
- повреждённая/отсутствующая active ссылка →503, без fallback на старую разрешающую политику.

Повторная выдача **уже выполненной** операции по прежнему idempotency key не является новым действием и не повторяет запись.

## Retention

По умолчанию audit events хранятся 7 дней. `ASTRAGUARD_AUDIT_RETENTION_DAYS` допускает 1..30 дней; некорректная конфигурация останавливает запуск.

Очистка при открытии БД и затем по часовому таймеру lifespan удаляет audit events старше retention, истёкшие approvals и execution-cache. Policy history, активная политика и synthetic resources сохраняются. API stats указывает окно min(7, retention_days).

Ошибка фоновой очистки переводит readiness в degraded. Ошибка обязательной записи audit, как и раньше, предотвращает действие. SQL DELETE не гарантирует физическое стирание WAL/backup/диска; шифрование SQLite не заявляется.

Migration v2 →v3 сохраняет существующие данные и политики. Более новая неизвестная версия не открывается с понижением. YAML seed не откатывает активную версию после рестарта.

## Проверки этапа

**114 offline tests passed**, одно известное предупреждение TestClient backend. Новые тесты: авторизация admin, ETag/version, immutable history/restart, неотменяемые tenant/write barriers, audit rollback, конкурентные updates, policy change во время detector/executor/approval grant, повреждённая active ссылка, unsafe YAML и retention на старте.

Часовой timer подключён к lifespan; тест очистки не ждёт час, а проверяет реальное удаление при повторном открытии SQLite. Длительная надёжность обслуживания здесь не измерялась.

Браузерный smoke с реальным Ollama на отдельной БД прошёл: requester/reviewer flow, вход policy-admin, успешный PUT, 412 для старого ETag, немедленный BLOCK для viewer по новым ACL и восстановление прав новой версией. Admin UI просмотрен в Chrome.

Новые Precision/Recall в этом этапе не измерялись. Значения EVALUATION.md относятся к указанным там commit/source hashes.

Startup/digest и сохранение состояния неопределённой генерации реализованы в [DETECTOR_LIFECYCLE.md](DETECTOR_LIFECYCLE.md). Остаются расширение интеграционных контрактов и независимая оценка новых семейств атак.
