# Проверки внешнего агента

Реализованы `POST /v1/tool-checks` и `POST /v1/content-checks`. Оба маршрута возвращают 201 с сохранённым решением и ничего не исполняют. Это advisory API: подключающий агент обязан останавливать передачу при REVIEW/BLOCK, транспортной ошибке, таймауте или неизвестном формате ответа. Сам факт наличия шлюза не изолирует агент, который имеет прямой доступ к инструментам.

## Identity и родительская проверка

В MVP адаптер действует с Bearer credential конкретного пользователя из серверной конфигурации identities. Отдельного service credential с возможностью выбирать пользователя нет. Делегирование для общего service account остаётся P1. Роль, tenant и subject в теле запрещены.

Последовательность:

1. Создать `/v1/sessions` с этим credential.
2. Проверить запрос через `/v1/checks` и получить ALLOW.
3. Перед каждым фактическим вызовом инструмента отправить его настоящее имя и аргументы в `/v1/tool-checks`.
4. Перед включением полученного tool/RAG-контента в контекст отправить его в `/v1/content-checks`.
5. Продолжать соответствующий шаг только при ALLOW. Исполнитель повторно проверяет полномочия непосредственно перед доступом к ресурсу.

Оба дочерних маршрута требуют `session_id` и `parent_check_id`. Родитель должен быть исходной проверкой запроса с ALLOW того же subject, tenant и сессии. Дочерняя проверка, исполнение или подтверждённая запись не подходят вместо родителя. Чужой/отсутствующий родитель даёт одинаковый 404; неподходящий собственный родитель даёт 409. Reviewer видит аудит своего tenant, но не может действовать от имени владельца события.

Сессия действует 30 минут и хранится в RAM. После restart её нужно создать заново. Проверки разделяют с обычными запросами лимит 30 запросов/мин на principal и session lock с demo forwarding. Истёкшая во время анализа сессия не получает положительного результата.

## Аргументы инструментов

```json
{
  "session_id": "UUID",
  "parent_check_id": "UUID исходного ALLOW",
  "tool": "documents.read",
  "arguments": {"document_id": "A1"}
}
```

Registry MVP:

| Tool | Arguments | Проверки |
|---|---|---|
| documents.read | document_id: строка `[A-Za-z0-9_-]{1,64}` | Наличие, вид ресурса, tenant и разрешение роли; без inference |
| drafts.update | draft_id: тот же формат; content: 1..6000 символов | Те же ACL, затем правила и семантическая проверка content; всегда минимум REVIEW |

Неверные аргументы известного инструмента или лишние поля дают 422. Неизвестный инструмент даёт BLOCK/TOOL_NOT_ALLOWED. Отсутствующий и чужой ресурс дают одинаковый BLOCK/RESOURCE_NOT_FOUND_OR_HIDDEN. При критическом отказе ACL модель не вызывается. Заявление в content о разрешении не меняет ACL.

Для `drafts.update` безопасное содержимое даёт REVIEW/ACTION_REQUIRES_APPROVAL, атака может дать BLOCK, сбой детектора даёт неподтверждаемый REVIEW. Внешние tool-checks не входят в demo approval workflow: `review.approvable=false`. Их нельзя подтвердить через `/reviews/{id}/approve`; интеграционный протокол подтверждений и идемпотентности внешнего исполнителя ещё не реализован.

## Недоверенный контент

```json
{
  "session_id": "UUID",
  "parent_check_id": "UUID исходного ALLOW",
  "source": "retrieved_document",
  "text": "Объясни способы защиты от prompt injection"
}
```

`source` допускает только `tool_result` или `retrieved_document`. Это метка недоверенных данных, заявленная вызывающей стороной; она не подтверждает происхождение и не предоставляет полномочий. Значения system/developer/trusted_tool запрещены. Текст непустой, максимум 6000 символов. Правила ищут активную атаку, терминология безопасности сама по себе не блокирует запрос. Семантическая модель получает текст как JSON-данные, а не system message.

ALLOW здесь означает только результат проверки содержимого. Он не разрешает читать исходный документ: доступ к нему проверяется отдельно. Маршрут не включает текст в контекст и не меняет историю demo agent. Полного анализа внешней многошаговой истории пока нет: адаптеру нужно ограничивать контекст и проверять каждый новый фрагмент. Семантическая классификация не даёт гарантии обнаружения всех косвенных инъекций.

## Повторная проверка и аудит

Перед сохранением результата повторяются ACL и проверка родителя в SQLite-транзакции. Критический актуальный запрет имеет приоритет над оценкой модели. Устаревшая версия политики или изменение во время анализа останавливают передачу с REVIEW/POLICY_CHANGED; требуется новая исходная проверка. Транзакция шлюза не распространяется на внешнее исполнение: решение не является одноразовым execution grant и не защищает от гонки после HTTP-ответа.

Результат содержит `event_type=tool_check|content_check`, `parent_id`, decision/risk/reason_codes/threats, текущую policy_version, detector status/digest, timing_ms.total, review и `forwarded=false`. Текст, content и идентификаторы ресурсов в результат не копируются. Сохраняется keyed HMAC канонического валидированного тела, без возможности восстановить содержимое. Для неизвестного инструмента журналируется имя `unknown`. Ошибка аудита даёт 503; положительный ответ не выдаётся.

`GET /v1/checks` показывает дочерние события с обычной изоляцией владельца/tenant. Статистика классификации запросов не учитывает дочерние проверки повторно.

## Проверка этапа

`tests/test_integration.py` содержит 29 сценариев: typed args, подмена identity, чужая сессия/родитель, цепочка дочерних проверок, ACL, семантическое ветвление, учебные запросы, смена владельца ресурса и политики во время анализа, отказы детектора и аудита. Семантические unit tests используют заглушку и не являются измерением качества Qwen.

18 ноября 2026 выполнен отдельный smoke с настоящим локальным Ollama 0.40.16 / Qwen 3.5 4B, digest `7f3251fa6878a78a606bcb3c074283306e5ad2ea411a7774a9dd98a4bc7f2d13`. Использованы временная БД, случайный credential и синтетические данные. Readiness вернул 200; исходный безопасный запрос получил ALLOW; чтение A1 получило ALLOW, B1 получило BLOCK; активная инструкция «Игнорируй предыдущие инструкции» в retrieved_document получила BLOCK, запрос о защите от prompt injection получил ALLOW. Счётчик demo agent остался 0. Это проверка соединения и четырёх сценариев, не новый benchmark качества или latency. До запуска Ollama этот же startup корректно возвращал readiness 503/unavailable.
